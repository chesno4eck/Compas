# Рекомендации по оценке: Backend-разработчик

Навык SFIA общий. Ниже — что проверять **в контексте этой роли**. Если навыка нет в списке — используйте универсальный текст SFIA.

## PROG — Программирование / разработка ПО

### Уровень 2

**Проверять:**

- Пишет простые хендлеры и утилиты на Go (структуры, ошибки, слайсы) по задаче
- Использует Gin на типовых задачах под менторством: роут, хендлер, JSON-ответ
- Не хранит секреты в коде; логирует через slog по образцу команды
- Перед сдачей сам просматривает свой PR, правит замечания

**Артефакты:**

- PR с простой фичей или багфиксом
- Простой unit-тест по образцу команды

### Уровень 3

**Проверять:**

- Самостоятельно закрывает фичу целиком: хендлер, сервис, доступ к данным (PostgreSQL / Redis), ошибки и логирование
- Уверенно применяет Go: context, интерфейсы, обработка ошибок; следует слоям команды (Gin, пакеты)
- Пишет и дополняет unit-тесты на новую логику; участвует в ревью кода
- Описывает HTTP API в OpenAPI по принятому шаблону команды

**Артефакты:**

- PR фичи с хендлером, доступом к данным и обработкой ошибок
- Ревью с содержательными комментариями
- Разбор бага с корневой причиной в тикете

### Уровень 4

**Проверять:**

- Реализует сложные модули и интеграции: контракты OpenAPI, кэш Redis, асинхронные сценарии; понимает, когда уместен gRPC вместо HTTP
- Влияет на выбор подходов, зависимостей и практик безопасности; оценивает Kafka и другие интеграции под задачу
- Ведёт ревью коллег; проводит рефакторинг устаревшего кода с сохранением поведения
- Оценивает риски релиза (регрессии, миграции goose, обратная совместимость API)

**Артефакты:**

- ADR или RFC по контракту API, модульности или асинхронной интеграции
- Серия ревью с планкой качества
- Рефакторинг с метриками / разбор инцидента

### Уровень 5

**Проверять:**

- Берёт тех. ответственность за бэкенд-стрим: от требований до поставки и оценки качества
- Планирует разработку: HTTP или gRPC, синхрон или Kafka, границы сервисов и feature-флаги — под задачу и контекст
- Контролирует стандарты команды, включая slog, метрики Prometheus и безопасность зависимостей
- Вносит вклад в руководства по бэкенд-разработке сообщества или организации

**Артефакты:**

- Принятые стандарты и гайды
- План тех. инициативы с метриками успеха
- Менторство с измеримым ростом людей

## SWDN — Проектирование ПО

### Уровень 2

**Проверять:**

- Описывает простой хендлер или пакет: ответственность, входы и выходы, базовый поток данных
- Применяет паттерны команды (слои хендлер / сервис / репозиторий) под контролем

**Артефакты:**

- Схема или короткая заметка по дизайну к задаче
- Диаграмма потока запроса

### Уровень 3

**Проверять:**

- Проектирует умеренно сложный модуль: слои, интерфейсы, ошибки, контракт OpenAPI
- Учитывает транзакции, идемпотентность и базовые нефункциональные требования

**Артефакты:**

- Проектный документ модуля
- Интерфейсы пакетов / контракт API в PR

### Уровень 4

**Проверять:**

- Проектирует сложные модули и интеграции с компромиссами (модульность, тестируемость, производительность, HTTP vs gRPC, синхрон vs Kafka)
- Ведёт ревью дизайнов коллег; прототипирует спорные решения

**Артефакты:**

- ADR с разбором альтернатив
- Ревью архитектурного предложения

### Уровень 5

**Проверять:**

- Задаёт подход к проектированию и архитектуре для крупной зоны бэкенд-продукта
- Балансирует качество, безопасность и поддерживаемость; влияет на стандарты проектирования

**Артефакты:**

- Архитектурные принципы стрима
- Анализ влияния крупного изменения

## SINT — Интеграция систем и сборка

### Уровень 2

**Проверять:**

- Собирает сервис (`go test ./...`, `go build`) или по CI-инструкции команды, прогоняет заданные проверки
- Фиксирует падения сборки и тестов с воспроизведением

**Артефакты:**

- Лог успешной или упавшей сборки
- Скрин задачи CI

### Уровень 3

**Проверять:**

- Настраивает зависимости модуля (`go.mod`), понимает миграции goose и конфиг сервиса
- Чинит типовые поломки CI; добавляет интеграционный тест на критичный путь фичи

**Артефакты:**

- PR с правкой go.mod, миграции goose или конфига CI
- Интеграционный тест на основной сценарий фичи

### Уровень 4

**Проверять:**

- Проектирует сложные интеграции и сборки: контракты OpenAPI с клиентами, Kafka, gRPC, ускорение CI
- Согласует интеграцию с iOS-, Android- и frontend-командами; развивает интеграционные тесты в пайплайне

**Артефакты:**

- Ускорение пайплайна с метрикой времени
- План интеграции крупной фичи

### Уровень 5

**Проверять:**

- Развивает CI/CD и практики интеграции бэкенд-направления
- Выбирает инструменты сборки, контрактов и доставки, задаёт стандарты

**Артефакты:**

- Стандарт CI для бэкенда
- Внедрение новых инструментов сборки или контрактов

## TEST — Функциональное тестирование

### Уровень 1

**Проверять:**

- Прогоняет готовые тесты и чеклист по своей задаче под наставничеством

**Артефакты:**

- Отмеченный чеклист в тикете
- Лог прогона существующих тестов

### Уровень 2

**Проверять:**

- Пишет unit-тесты на свою логику: основной сценарий и базовые негативные
- Заводит баги с шагами, окружением, ожидаемым и фактическим результатом

**Артефакты:**

- Unit-тесты в PR
- Заведённый баг с полным описанием

## NFTS — Нефункциональное тестирование

### Уровень 2

**Проверять:**

- Смотрит Grafana / Prometheus и логи OpenSearch на явные проблемы своей фичи
- Ловит очевидные медленные запросы (EXPLAIN) и лишние обращения к PostgreSQL или Redis

**Артефакты:**

- Скрин или заметка дашборда / EXPLAIN
- Фикс латентности или лишних запросов в PR

### Уровень 3

**Проверять:**

- Планирует простые проверки производительности и стабильности для рискованных изменений
- Умеет интерпретировать базовые метрики сервиса в Grafana и логи в OpenSearch

**Артефакты:**

- Короткий чеклист нефункциональных проверок к релизу фичи
- Разбор деградации латентности или ошибок

## METL — Методы и инструменты

### Уровень 2

**Проверять:**

- Работает в IDE и Git по гайдам команды; применяет goose и slog по образцу; обновляет README по просьбе

**Артефакты:**

- PR по шаблону команды

### Уровень 3

**Проверять:**

- Настраивает линтеры, форматтеры и тестовые хелперы в своём пакете; чинит типовые проблемы с инструментами

**Артефакты:**

- PR с конфигом линтера, Makefile или тестовым хелпером

### Уровень 4

**Проверять:**

- Рекомендует и внедряет инструменты бэкенд-команды (покрытие тестами, gRPC, миграции); пишет короткие гайды

**Артефакты:**

- Гайд по инструменту
- Внедрение шаблона тестов, генератора или клиента gRPC

### Уровень 5

**Проверять:**

- Выбирает набор инструментов для направления; оценивает их пользу

**Артефакты:**

- Решение о выборе инструмента с критериями
- Политика использования AI/IDE в команде

## RELM — Управление релизами

### Уровень 2

**Проверять:**

- По чеклисту готовит материалы релиза (заметки, миграции goose) под контролем

**Артефакты:**

- Заполненный чеклист релиза

### Уровень 3

**Проверять:**

- Проводит типовой релиз фичи в прод по процессу команды
- Ловит блокеры релиза, включая миграции

**Артефакты:**

- Релиз-ноты и статус раскатки

### Уровень 4

**Проверять:**

- Планирует релиз с зависимостями, поэтапной раскаткой, feature-флагами и порядком миграций

**Артефакты:**

- План релиза
- Разбор после релиза

## DBDS — Проектирование баз данных

### Уровень 2

**Проверять:**

- Пишет простые миграции goose и CRUD-запросы к PostgreSQL под менторством
- Использует Redis по образцу команды (ключ, TTL) под контролем

**Артефакты:**

- PR с простой миграцией и запросом
- Заметка по ключу Redis, если использовался

### Уровень 3

**Проверять:**

- Самостоятельно проектирует таблицы, индексы и миграции для фичи
- Выбирает, что кэшировать в Redis; понимает транзакции и типовые ловушки (N+1, отсутствие индекса)

**Артефакты:**

- Миграция goose с индексами и ограничениями
- EXPLAIN или заметка по запросу в PR

### Уровень 4

**Проверять:**

- Проектирует схемы с учётом нагрузки, доступности и эволюции API
- Оценивает альтернативы хранения (PostgreSQL vs MongoDB vs Redis) и аргументирует выбор
- Ревьюит миграции и запросы коллег

**Артефакты:**

- ADR по схеме или выбору хранилища
- Ревью миграции с замечаниями по индексам и нагрузке

## DTAN — Моделирование и проектирование данных

### Уровень 2

**Проверять:**

- Описывает простые сущности и связи фичи под руководством
- Следует принятой модели данных сервиса

**Артефакты:**

- Короткая схема сущностей к задаче

### Уровень 3

**Проверять:**

- Моделирует данные фичи: сущности, связи, ограничения
- Объясняет, когда документная модель (MongoDB) уместнее реляционной, и когда нет

**Артефакты:**

- Модель данных фичи
- Заметка с обоснованием модели хранения
